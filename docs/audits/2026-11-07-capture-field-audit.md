# Questionnaire / legacy intake field audit (read-only)

Scope: source inspection only, no student data or production access. JSON contains every statically enumerated consultation field, every legacy IntakeForm setter, expanded 7×3 work schedule keys, and type-only legacy keys. Question wording copied when statically available; type-only labels are explicitly inferred identifiers, not approved prompts. The consultation student form and admin instructor entry use the SAME QuestionnaireForm; StrategyConsultationReport displays SECTIONS without additional persisted answers. Consultation types.ts is narrower/different than actual UI keys; student-data.ts allowlist includes additional historical keys.

## Critical findings

- compatibility.ts is an identity source-wrapper, NOT a mapper; no existing cross-population into V2.
- Legacy student_intake completion simply sets completed status; it does not establish V2 completeness. Never convert completed status to known answers.
- hoursPerWeek has a dangerous semantic collision: ConsultationQuestionnaireData section B defines employment hours, whereas current questionnaire section G labels it study/practice availability. Map only with known source form/version.
- installed MT5, historical MT4/MT5 use, current access, proficiency, and demonstrated execution are different facts. mt45=Yes cannot identify MT5. broker name, broker preference, broker experience, current broker account, and live/demo activity are different facts.
- Seven legacy knowledge ratings cannot fill 13 V2 topics. None/Basic/Intermediate/Advanced/Expert are self-report evidence, not automatically approved V2 ratings or mastery. Combined SL/TP cannot independently prove either practical skill. Preserve unmapped evidence.
- Exact financial amounts may derive approved ranges only with currency/cadence/bracket definitions; rent cannot prove housing status; listed bills cannot prove total obligations without completeness. Savings != emergency fund. Desired total income != desired additional income != desired trading income.
- Legacy goals6–12 combined narrative cannot be split into exact 6- and 12-month answers; personal/life 12-month goal != financial goal != competency goal. Keep narrative intact.
- student-data.ts accepts arrays ONLY for marketsTraded/platformsUsed/learningMethods/preferredStudyTimes, yet current form stores learningPrefs/accountabilityPrefs/devices/focusAreas arrays; those arrays are omitted from student output by allowlist shape filtering. Treat as privacy/data fidelity issue, never broaden private key exposure.
- Questionnaire M instructor keys are excluded from student form, unknown keys private by default. Keep all observations/recommendations private until separately approved projection. Do not use instructor self-assigned level as student-reported experience.

## Completion / conditional mismatches

- V2 liveHasExperience treats any nonempty live != No as experience; unfamiliar/PNTS/not-yet-experience choices may spuriously require liveAccountSizeRange. Must compare actual approved choices before changing.
- priorEdHasYes similarly treats any nonempty type != No as requiring notes; uncertain/PNTS can spuriously trigger. brokerHasExperience and negativeExpHasDetail are unused helpers.
- knowledgeMatrix and behaviorMatrix validation checks only object key counts (13/5), not required topic membership/nonempty ratings; malformed extra keys can pass.
- weeklyAvailability validation checks only nonempty object; empty day windows can pass. unavailableDays requires a nonempty selection: valid explicit None option must exist rather than fabricated absence.
- Phase3f version currently requires PF only; MO required only phase3d/e and TC only phase3e. This means newest drafts can omit MO/TC. Comments express version policy but don't include later version. Determine approved policy before editing.
- Debt/DC conditional Yes checks are appropriately exact; hidden DC stale values do not block. MO subranges apply exact Yes/status; optional notes only max length. Financial PNTS valid, must retain as response and never normalize to zero.
- V2 requires 12 instructor fields (summary, assessed experience, assessed knowledge, strengths, weaknesses, starting level, academy track, first lesson, homework, practice/coaching frequency, immediate actions); three high-risk concern/restriction fields conditional. Replacing summary UI alone will not remove manual completion barrier. Judgment fields must remain judgment; system recommendation approval should be explicit.
- Current consultation completion heuristics inspect only sparse section fields; admin complete allows even no data after confirmation. It cannot certify current V2 completeness.
- Acknowledgment booleans from legacy are NOT equivalent to seven audited V2 acknowledgments; do not invent audit records or confirmations.

## Canonical authority and consumers

Use existing Intake V2 student_sections_json.{key}.value and provenance for exact facts, not parallel editable summary copies. Persist no inferred default for unknown values. Instructor-entered-for-student is capture mode, NOT instructor observation. Current ProvenanceSource lacks separate observed, assessment-demonstrated and override sources: introduce additive evidence metadata carefully rather than abusing student values. Derived displays should reference field paths/source record and actor/time. Preserve legacy questionnaire revisions and legacy student_intake versions.

Consumer categories: financial income/expenses/debt/capital/goals → FINANCIAL_READINESS_INPUT, never educational competency; markets/platform experience/knowledge/risk practice → EDUCATIONAL_PLACEMENT_INPUT and LEARNING_PATH_INPUT as self-report only; personal goals → LEARNING_PATH_INPUT/INFORMATIONAL_ONLY (financial goal cannot change competency); learning/accountability/schedule → SUPPORT_PREFERENCE and LEARNING_PATH_INPUT; device/internet/platform access → ACADEMY_READINESS; instructor raw notes → INSTRUCTOR_PRIVATE. Instructor track/start/plan/actions are legacy recommendations, not independent placement authority; retain historical data, present system recommendation plus explicit approval/override with reason.
